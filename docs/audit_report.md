# Экспертный технический аудит: Bo Landing Page / Universal Restaurant Platform

## 1. Резюме (Executive Summary)
Проект находится в активной фазе трансформации из лендинга одного ресторана (Bo Dubai) в **универсальную SaaS-платформу** для ресторанного бизнеса. Текущая архитектура на базе Next.js и Firebase закладывает отличный фундамент для масштабирования, однако переход к мультиарендности (multi-tenancy) на данный момент реализован частично и содержит элементы "хардкода", которые могут замедлить масштабирование.

**Основные показатели:**
- **Стек:** Next.js 14, Tailwind CSS, Firebase (Firestore, Auth, Storage), Framer Motion.
- **Готовность к SaaS:** 65% (архитектура готова, данные частично изолированы).
- **Дизайн:** Высокий уровень эстетики, адаптивность, наличие геймификации (Shake-to-Win).

---

## 2. Анализ Архитектуры и Масштабируемости

### 🟢 Сильные стороны
- **Изоляция темы (Theme Injection):** Использование CSS-переменных, инжектируемых в `:root` через `dangerouslySetInnerHTML` в `layout.tsx`, — это элегантное решение для динамического брендинга без пересборки приложения.
- **Firebase Security Rules:** Правила хорошо структурированы, поддерживают RBAC (Role-Based Access Control) и логику изоляции тенантов.
- **Middleware:** Наличие заготовки для защиты админ-роутов и потенциальной маршрутизации по доменам.

### 🔴 Точки роста (Технический долг)
- **Repetitive Content:** Файлы `content.ts` и `tenant.ts` содержат дублирующуюся логику переключения (тернарные операторы по `NEXT_PUBLIC_TENANT_ID`). При добавлении 3-го и 4-го тенанта этот подход станет неуправляемым.
- **Hardcoded Schema:** В `app/lib/schema.ts` данные для JSON-LD (Restaurant, Menu) захардкожены под Bo Dubai (валюта AED, название "Bo"). Это критично для SEO других тенантов.
- **Singleton Config:** `tenantConfig` экспортируется как константа, определяемая во время сборки. Это ограничивает возможность использования одной сборки для нескольких доменов (нужен переход на динамическое определение тенанта по `host`).

## 3. Фронтенд, UX и Дизайн

### 🟢 Сильные стороны
- **Анимации:** Использование `framer-motion` и `canvas-confetti` создает "premium feel" и повышает вовлеченность.
- **PWA:** Наличие `manifest.ts` и `InstallPrompt` делает приложение удобным для использования как "WebApp" на смартфонах.
- **Геймификация:** Модуль `ShakeToWin.tsx` — отличный маркетинговый инструмент, выделяющий проект среди конкурентов.

### 🔴 Рекомендации
- **Оптимизация LCP:** Изображения в Hero-секции и меню требуют более агрессивной оптимизации через `next/image` с правильными `priority` и `sizes`.
- **Компонентная чистота:** Модальные окна (Booking, Menu) достаточно тяжелые. Рекомендуется использовать динамические импорты (`next/dynamic`) для загрузки кода модалок только при открытии.
- **VibeCheck:** Текущая логика смены "вайба" меняет только фильтрацию меню. Можно усилить эффект, меняя CSS-переменные акцентного цвета или фонового градиента в зависимости от выбранного вайба.

## 4. SEO и Локализация

### 🟢 Сильные стороны
- **Multi-language:** Поддержка EN, RU, VN, AR реализована через App Router `[lang]`.
- **Metadata API:** Используется современный Next.js Metadata API с поддержкой OpenGraph и Twitter Card.

### 🔴 Точки роста
- **Динамический Sitemap:** Текущий `sitemap.ts` возвращает статический список URL. Для платформы он должен генерироваться на основе данных из Firestore (меню, категории).
- **JSON-LD Schema:** Необходимо сделать `getRestaurantSchema` зависимым от `tenantConfig`.
- **Локализация Luna & Co:** Вьетнамский перевод (`vn`) в `content.ts` выглядит качественным, но требует проверки нативных носителей для ресторанного контекста Хошимина.

---

## 5. Безопасность и Надежность

### 🟢 Сильные стороны
- **Firestore Rules:** Разделение на `tenants/{tenantId}` — это "золотой стандарт" для Firebase SaaS.
- **Admin Verification:** Проверка по email-паттерну (`.*@bo-restaurant.com`) — хорошее временное решение для безопасности.

### 🔴 Критические замечания
- **Тестирование:** `homepage.spec.ts` завязан на текст "Bo Restaurant Dubai". Тесты упадут при смене тенанта. Нужно использовать `data-testid` или переменные из конфига.
- **Error Boundaries:** Недостаточно обработки ошибок при сбое загрузки конфига из Firestore. Приложение может "упасть" в белый экран.

## 6. План действий (Action Plan)

### Фаза 1: Срочные исправления (Quick Wins)
1.  **Dynamic SEO:** Сделать `JsonLd` и `getRestaurantSchema` полностью зависимыми от `tenantConfig`.
2.  **Test Stability:** Переписать Playwright тесты на использование `tenantConfig.brand.name` вместо жестких строк.
3.  **Image Optimization:** Добавить `priority` к Hero-изображениям.

### Фаза 2: Рефакторинг под SaaS (Universal Template)
1.  **Configuration Provider:** Вместо импорта `tenantConfig` напрямую, создать `TenantContext`, который будет инициализироваться данными из Firestore при загрузке.
2.  **Centralized Content:** Вынести `content.ts` в Firestore. Это позволит менять тексты без деплоя.
3.  **Domain Routing:** Обновить `middleware.ts` для определения `tenantId` на основе `request.nextUrl.hostname`.

### Фаза 3: Запуск Luna & Co (HCMC)
1.  **Media Assets:** Загрузить логотип и фон Luna в Firebase Storage.
2.  **Pricing Format:** Убедиться, что для VND (`precision: 0`) разделители тысяч настроены корректно (100.000 ₫ вместо 100,000.00 ₫).
3.  **Zalo Integration:** Поскольку это Вьетнам, добавить кнопку Zalo в `FloatingChat`.

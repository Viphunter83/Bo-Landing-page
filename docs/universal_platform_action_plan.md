# Глубокий анализ проблем и план перехода к Universal Platform (Global Restaurant Template)

## 1. Анализ текущей ситуации и причин нестабильности (500 / 401 / 404 ошибки)

Несмотря на отключение защиты SSO и восстановление `middleware.ts` с защитными проверками, продакшен на Vercel продолжает вести себя нестабильно. Вот основные архитектурные и инфраструктурные причины происходящего:

### А. Конфликт статической генерации (SSG) и Middleware (Edge Runtime)
1. **Дублирование корневых роутов**: У нас существует `app/page.tsx` (корневая страница) и `app/[lang]/page.tsx` (локализованная страница). Middleware жестко редиректит `/` на `/[lang]`. В Next.js наличие обоих файлов при агрессивном кэшировании может приводить к путанице маршрутизатора на Edge-уровне Vercel (выдавая 404 для неопознанных путей).
2. **Build-Time vs Runtime Конфигурация**: Наш файл `app/layout.tsx` импортирует `tenantConfig` (который опирается на `process.env.NEXT_PUBLIC_TENANT_ID`) и использует его для генерации статических метаданных (`export const metadata`). Если во время билда переменная окружения не пробросилась или закешировалась некорректно, весь сгенерированный статический сайт становится неконсистентным.
3. **Data Cache Vercel**: Ошибки 500 и 401 могут "залипать" в кэше CDN Vercel. Если первая сборка упала или попала на включенный SSO, Vercel Edge Network может отдавать закэшированный ответ 401/500 даже после отключения защиты в настройках.

### Б. Проблема авторизации и сессий в Edge
Middleware пытается прочитать куку `bo_session`. Если процесс логина Firebase работает некорректно или кука устанавливается с неверными параметрами (`Secure`, `SameSite`, `Domain`), Edge Middleware её просто не видит и уводит пользователя в бесконечный цикл редиректов или выдает 500 при попытке распарсить невалидные заголовки.

---

## 2. Перечень выявленных проблем (Problem List)

1. **Инфраструктурный "призрак" SSO**: Настройки защиты деплоя в Vercel требуют полной пересборки (Clear Cache & Redeploy) для применения.
2. **Мертвый код и конфликты роутинга**: `app/page.tsx` конфликтует с логикой `middleware.ts` по обработке корня сайта.
3. **Жесткая привязка конфигурации к коду**: `tenant.ts` не позволяет менять настройки ресторана без нового деплоя, что убивает концепцию "Универсальной платформы".
4. **Непрозрачность логов Edge Middleware**: В случае падения `try/catch` мы видим логи только в консоли Vercel (которую нужно специально мониторить), но пользователю отдается стандартная заглушка без контекста.
5. **Риск пересечения данных (Data Leakage)**: Пока `tenantId` не внедрен глубоко в правила безопасности Firestore, любая ошибка в клиентском запросе может показать данные Bo Restaurant в приложении Luna & Co.

## 3. Детальный план действий (Action Plan) для реализации в новом чате

План разделен на 3 фазы: **Стабилизация текущего продакшена**, **Рефакторинг под Universal Platform**, и **Внедрение полной изоляции**.

### Фаза 1: Жесткая стабилизация (Hotfixes & Infrastructure)
*Цель: Добиться того, чтобы сайт открывался без ошибок 401/500/404 на продакшене.*

1. **Зачистка кэша и принудительный деплой**:
   - В Vercel запустить `Redeploy` с галочкой "Use existing build cache" -> **ВЫКЛЮЧЕНО** (полностью чистая сборка).
   - Убедиться, что `NEXT_PUBLIC_TENANT_ID` жестко прописан в Production Environment Variables в панели Vercel.
2. **Устранение конфликта роутинга**:
   - Удалить `app/page.tsx`.
   - Настроить `next.config.js` для встроенного `redirect` или `rewrite` с `/` на `/[defaultLocale]`, чтобы разгрузить Middleware.
3. **Мониторинг Middleware**:
   - Временно добавить уникальные HTTP заголовки в ответы `middleware.ts` (например, `x-tenant-id: luna_hcmc`), чтобы через DevTools браузера точно понимать, отрабатывает ли новая версия Middleware или мы смотрим на кэш.

### Фаза 2: Архитектура Universal Platform (Decoupling)
*Цель: Оторвать конфигурацию от кодовой базы и перейти к динамическому управлению.*

1. **Миграция конфигураций в Firestore**:
   - Создать коллекцию `tenants` в Firebase.
   - Перенести объекты `boConfig` и `lunaConfig` в документы `tenants/bo_restaurant` и `tenants/luna_hcmc`.
   - Написать слой доступа к данным (`lib/firebase/tenant.ts`), который будет делать `getDoc(doc(db, "tenants", tenantId))` на сервере (в React Server Components).
2. **Адаптация UI под динамический конфиг**:
   - Обновить `app/layout.tsx` и `[lang]/layout.tsx` для асинхронного получения `tenantConfig` перед рендерингом стилей и метаданных.
   - Использовать `unstable_cache` или `fetch(..., { next: { tags: ['tenant-config'] } })` для обеспечения мгновенной загрузки (как при статической генерации).

### Фаза 3: Изоляция данных и безопасность (Multi-tenancy Security)
*Цель: Гарантировать, что менеджер Luna никогда не увидит заказы Bo, и наоборот.*

1. **Рефакторинг запросов к БД**:
   - Обновить все Firebase хуки и серверные экшены: `collection(db, 'orders')` -> `collection(db, 'tenants', tenantId, 'orders')`.
2. **Firebase Security Rules**:
   - Написать строгие правила: `match /tenants/{tenant}/orders/{order} { allow read, write: if request.auth.token.tenant == tenant; }`
3. **Обновление системы авторизации**:
   - При логине администратора, через Firebase Custom Claims присваивать пользователю его `tenantId`.
   - В `middleware.ts` добавить расшифровку токена (через легкую библиотеку, совместимую с Edge, например `jose`) для проверки принадлежности админа к текущему домену.

---
**Итог:** Этот план позволит нам не просто "починить баг", а перевести проект в статус настоящего SaaS-решения, где запуск нового ресторана будет занимать 5 минут (копирование проекта в Vercel + создание документа в Firestore).

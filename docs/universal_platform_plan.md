# План перехода на универсальную платформу (Global Restaurant Template)

## 1. Текущее состояние
- Проект уже поддерживает базовую мультитеннтность через `NEXT_PUBLIC_TENANT_ID`.
- Конфигурации `boConfig` и `lunaConfig` жестко прописаны в `app/lib/config/tenant.ts`.
- Используется одна кодовая база для разных проектов в Vercel.

## 2. Целевая архитектура (Universal Template)

### А. Управление конфигурациями
- **Этап 1 (Текущий)**: Добавление новых объектов в `tenant.ts`.
- **Этап 2 (Масштабирование)**: Вынос конфигураций в Firestore. При загрузке приложения (или в `getStaticProps`/`getServerSideProps`) конфиг подтягивается по `TENANT_ID`.

### Б. Изоляция данных (Firebase)
Для обеспечения безопасности и разделения заказов/клиентов между ресторанами:
- Все коллекции в Firestore будут использовать `tenantId` как префикс или как обязательное поле.
- **Пример**: `tenants/{tenantId}/orders/{orderId}` или общая коллекция `orders` с фильтром по `tenantId`.
- **Security Rules**: Обновление правил Firestore для запрета доступа к данным другого тенанта.

### В. Динамический брендинг
- Использование CSS переменных (уже частично реализовано через `ThemeTokens`).
- Динамическая загрузка логотипов и изображений из Firebase Storage с путями `tenants/{tenantId}/assets/...`.

## 3. Технический стек для новых запусков
- **Frontend**: Next.js (Vercel).
- **Backend**: Firebase Functions (для уведомлений, API).
- **Database**: Firestore.
- **Auth**: Firebase Auth (общая база пользователей или раздельная).

## 5. Что менять в проде для масштабирования?
1. **Middleware**: Автоматическое определение тенанта по домену (например, `luna.com` -> `luna_hcmc`).
2. **Admin Panel**: Единая админка с переключателем контекста (для владельца сети) или изолированные админки для менеджеров конкретных ресторанов.
3. **Analytics**: Раздельные дашборды для каждого филиала.
